# 托管配置上下文（模板 = provider 的完整配置）—— 设计基线

> **状态：设计文档，尚未实施。**
> 本文档只定义 **P1（UI 重排）** 的范围与验收；P2/P3 仅记录、未排期。
> 与 `docs/hosting-templates.md`（阶段一：target 模板化）配套 —— 阶段一定义了「能力上限 + target 字段组」，本文档解决"账号级配置与发布行为还没收进模板"这个**半模板化**状态。

---

## 1. 背景

### 1.1 现状：provider 配置散落在三处

| 位置 | 内容 |
|---|---|
| 设置页「基础配置」区 | `cf_account_id` / `cf_api_token` / `cf_r2_bucket` / `cf_d1_database` / `cf_site_url` / `cf_auth_key`（各自独立 option）|
| 设置页「发布行为」行 | `cf_sync_d1` / `cf_gen_static` / `cf_publish_remote`（**全局一份**）|
| 设置页「🎯 托管目标」卡片 | `cf_hosting_targets`（每目标：模板 + 能力 + 意图 + endpoint/auth_key/bucket…）|

### 1.2 目标

**模板 = provider 的完整配置上下文**：选定 `cloudflare`，就在这个模板下填齐它需要的一切（账号级 + 站点级 + 能力 + 意图 + 发布行为）；
选定纯静态 provider，就只出现它需要的字段，**不出现 Cloudflare 特有的东西**。

**要解决的痛点**：新用户"不知道该在哪填"（选中了 Cloudflare 模板，却还要回到上面的基础配置区找 Account ID / API Token）。

---

## 2. 概念边界（三个不同的东西，别混）

| 概念 | 含义 | 现状 |
|---|---|---|
| **多托管目标** | 一个 WP 站把内容分发到 R2 / s3 / local **多个地方** | ✅ **已实现**，且是**单租户** |
| **多租户 SaaS** | 一套 Worker + 一份 D1 服务**多个不同域名**的站 | ❌ **未实现，本期不做** |
| **多站自治** | 一个人管多个站，每站一套部署 | ✅ 架构天然支持（每站一套 Worker/D1/KV/R2）|

### 2.1 关键结论：隔离放在「部署单元层」，不放「数据行层」

- 每站一套 Worker + D1 + KV + R2 ⇒ 每个 D1 只服务一个 WP 站 ⇒ `wp_id` 库内天然唯一。
- 对比"共享 D1 + `site_id`"：需改 schema、改**所有**查询、改 frontmatter 语义、还要防跨租户泄漏 —— 成本与风险都高得多。
- 代价仅一条：多站要多套资源（免费额度足够）+ 重复部署一次（可脚本化）。

> **因此本项目不引入 `site_id`**（`schema.sql` 里也确实没有：`posts.wp_id INTEGER PRIMARY KEY` 单列主键）。
> 若将来要做 SaaS 多租户，那是**独立产品线**（"Worker 纯 CMS"），须单独立项，不得混入本文档范围。

---

## 3. 三层归属（哪些该进模板、哪些留全局）

| 类别 | 内容 | 归属 |
|---|---|---|
| ① **provider 配置** | Account ID / API Token / R2 Bucket / D1 Database ID / 站点 URL / Worker Auth Key | **进模板**（下分账号级 / 站点级）|
| ② **能力绑定行为** | 发布行为（同步 D1 / 生成静态文件 / 上传远端）、发布后清缓存 | **进模板区，且按能力出现**（无 `d1` 的目标不出现"同步到 D1"）|
| ③ **插件运行参数** | 导出模式、批量大小、并发数、缓存 TTL、feed 条数、日志开关 | **留全局**（与 provider 无关）|

### 3.1 ① 内再分层：账号级 vs 站点级

| 层级 | 字段 | 说明 |
|---|---|---|
| **账号级** | Account ID、API Token | 一个 Cloudflare 账号下可有多个 R2/D1/Worker ⇒ 多站时**理论上可复用** |
| **站点级** | 站点 URL、Worker Auth Key、R2 Bucket、D1 Database ID | 每个站各一份 |

> **本期只做 UI 分区，不实现复用逻辑**（大部分用户只有一个目标）。分区是零成本排版选择，将来真要共享账号时不用重排版面。
> `API Token` 属敏感值，**保持独立 option**（便于将来做"保存后不回显"）。

## 4. 模板卡片的目标形态（UI）

```
[模板 cloudflare]
  ├─ 账号级（可被其它 Cloudflare 目标复用）
  │    Account ID / API Token
  ├─ 本目标
  │    站点 URL / Worker Auth Key / R2 Bucket / D1 Database ID
  ├─ 能力：静态文件 / 文章数据 / 渲染 / 缓存
  ├─ 意图：服务 md / 动态列表 / 静态 HTML / 备份
  └─ 发布行为（全局一份，标注"仅对具备相应能力的目标生效"）：
       同步到 D1 / 生成静态文件 / 上传到远端
```

**为什么发布行为在 P1 仍保持全局一份**：`cf_sync_d1` 等是**全局 option**，而模板卡片是**每目标一张**；
若直接塞进某张卡片，多目标时会**重复显示**。P1 的做法是把它放进**托管目标卡片区域内、目标列表下方**（视觉归拢 + 能力关联说明），
**下沉到 target** 留给 P2。

---

## 5. P1 范围（最高性价比的一步）

### 5.1 做什么

**把散落的 provider 配置在设置页上搬进模板卡片区域，并分区显示。**

- 纯 **UI 重排**：`cf_account_id` / `cf_api_token` / `cf_r2_bucket` / `cf_d1_database` / `cf_site_url` / `cf_auth_key` 的**字段名与 option 一律不变**（仍在同一个 `options.php` 表单内，只是换了显示位置）。
- 发布行为块移入托管目标卡片区域，并加一行"仅对具备相应能力的目标生效"。
- **零数据迁移、零后端改动**。

### 5.2 不做什么（明确排除）

- ❌ 不动 `cf_*` option 的名字、类型、存储格式
- ❌ 不动 `load_config()` 的 `site_url` / `auth_key` 派生链（阶段一硬约束，继续有效）
- ❌ 不动导出链（`export_post` / `publish_artifact` / `target_upload` / `target_delete` / `target_purge` 及 10 处 `d1_batch` 调用点）
- ❌ 不实现发布行为下沉（P2）、不实现账号级复用（P3）
- ❌ 不引入 `site_id`、不做多租户

### 5.3 验收标准

| # | 检查点 | 验证方式 |
|---|---|---|
| P1-a | 模板卡片区域内出现全部 6 个 provider 字段（Account ID / API Token / R2 Bucket / D1 Database ID / 站点 URL / Auth Key）| 渲染设置页 HTML，断言这 6 个 `name=` 出现在托管目标卡片区块内 |
| P1-b | **字段名与 option 不变** ⇒ 保存后数据语义与之前**逐字节兼容** | 保存前后 `get_option()` 对比 6 个 option 的值 |
| P1-c | 发布行为块进入托管目标卡片区域，并带能力关联说明 | 渲染 HTML 断言位置与文案 |
| P1-d | 分区可见（账号级 / 本目标 两区有明确标题）| 渲染 HTML 断言分区标题存在 |
| P1-e | 视觉体验（"选了 cloudflare 就看到这些字段"）| **人工核对**（无浏览器自动化）|
| P1-f | 旧行为不回归 | **硬门禁 A1 / A2 / A4**（派生链、D1 通路、导出链零改动）+ 回归：设置页其余控件照常工作 |

### 5.4 硬约束（沿用阶段一）

1. `load_config()` 的 `site_url` / `auth_key` 派生链**不得切断**。
2. 导出链函数与 10 处 `d1_batch` 调用点**零改动**。
3. 验证必须走真实入口（`update_option` / 表单），**不得以"反射改内存 config"作为通过依据**。

## 7. `wp_id` 与跨站风险

### 7.1 隔离部署下不存在同名

每站一套 D1 ⇒ 库内 `wp_id` 唯一 ⇒ 不存在"同一 wp_id 指向不同文章"。**不需要 `site_id`、不需要站点筛选器或额外导航层。**

### 7.2 唯一残留风险：跨站复制笔记

把 A 站的 md 笔记**连同 frontmatter** 拷到 B 站时，`wp_id` 仍是 A 站的值；若 B 站恰好有同 ID 文章，**pull 时会错认/覆盖**。

### 7.3 两个轻量解法（都不改 schema）

1. **frontmatter 带站点标识**（如 `site: doc.yuebin.uk`），pull 时校验来源；
2. **pull 时冲突检测**：目标 ID 已存在且内容不同 ⇒ **报冲突让人决定**，不静默覆盖。

> 解法 2 无论有没有解法 1 都该做 —— 属"静默状态改变必须可见"的同类原则（参见阶段一 `$adjustments` 回显）。

---

## 8. 开放问题

1. 发布行为块在 P1 的**具体位置**（目标列表上方 / 下方）；是否需要在视觉上与"目标列表"更明确地分隔。
2. 账号级/站点级分区若将来要做复用，是否引入"账号"这一层实体（多个目标引用同一账号）。
3. `API Token`（及未来的 s3 `secret_key`）**不回显**的实现方式与时机。
4. P2 是否需要在 P1 稳定运行一段时间后再启动（与 `hosting-templates.md` 的阶段二同节奏）。
