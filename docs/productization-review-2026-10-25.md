## 一、用户的原始诉求（记录在案）

1. 把 Cloudflare Worker CMS 从大项目里**剥离成一款独立产品**。
2. **首要任务：剥离内置文档库功能**，做成纯粹 CMS 产品。
3. 现状问题自述：产品线分散混乱；CMS 与 WP 同步插件**耦合了模板资源、部署逻辑**，体验不理想。
4. 设计思路：同步插件**分层**——基础层只做纯数据同步，一键部署/模板资源上传归高级功能，两者解耦但**同插件内不拆**。
5. 目标：主体业务逻辑不变，在此基础上评估优化点，理顺产品体系。

## 二、实测得出的现状（与自述有出入的地方）

### 2.1 四条线其实是「一拆三」的结果，不是一直有四条

`docs/plugins-positioning.md` §8 记录：**2026-10-22 已做三插件拆分**，从原单文件拆出三个可独立安装的插件。

| 线 | 实际载体 | 状态 |
|---|---|---|
| 1 Worker CMS | `cf/worker/`（19 文件 / 8,819 行） | 现役，未独立成仓 |
| 2 WP 同步插件 | `cfse-sync/`（v1.0.0，2026-10-21） | 已拆出，**但内嵌 `worker/` 全量源码副本（19 文件）** |
| 3 外观抓取 | `cfse-style/` | 已拆出，已解耦（只读不碰远端） |
| 4 静态托管 / MD 编辑器 | `cf-static-hosting/`（private）+ `cf/tools/obsidian-md-publisher/` | 与 CMS 主线弱相关 |

⚠️ **线 2 的「耦合」根源不是功能耦合，是源码拷贝耦合**：
`cfse-sync/worker/src/` 是 `cf/worker/src/` 的逐字节副本。
实测 7 个核心文件 md5 **全部一致**（刚同步过），但机制上是拷贝 ⇒ 下次改 CMS 忘了同步插件，就会出「两份实现漂移」。

### 2.2 真正的耦合点是 `routes.js` 的生成链

- `routes.js`（1,191 行）是**生成物**：`cf-static-export-pro.php:1664 sync_routes()` 从 `routes.template.js` 替换 4 个占位符产出。
- `cfse-sync.php:1195 handle_deploy_worker()` 每次部署前先调 `sync_routes()`。
- ⇒ **WP 插件的一次点击，会静默覆盖 Worker 侧对 `routes.js` 的任何手工改动。**
- ⇒ 对「CMS 作为独立产品自主演进」是**结构性阻断**：CMS 不能自己改路由。

### 2.3 文档库剥离：站已独立，代码还没删

- `cf-docs/` 已独立上线（`docs.yuebin.uk`，独立 Worker `cf-docs` + 独立 D1 `docs` + 独立 R2 `docs`，119 篇文档）。
- **但主仓侧清理 0 行落地**（`cf-docs/docs/design.md` §8 P3 阶段 ⏸ 暂缓，2026-09-29 决定）。
- 待清约 900 行：`worker/src/documents.js` 565 行 + `admin.js` 8 个端点 + `static/admin/app.js` 343 行 + `routes.*` 64 行 + `site.js` 1 行 + `schema.sql` + `tools/import-documents.mjs`。

## 三、三个必须先解决的阻断项（对外发布前）

| # | 问题 | 位置 | 为什么阻断 |
|---|---|---|---|
| 1 | `AUTH_KEY_SECRET` 一钥两用（签 JWT + 校验 `/upload` `/delete` `/purge-cache` `/d1-batch` 四写通道） | `admin.js:884` + `routes.js` 8 处 | 拿到同步密钥即可自行签发 `role:'admin'` JWT，绕过登录 |
| 2 | 硬编码回退 `env.AUTH_KEY_SECRET \|\| 'cfse-dev-secret'` | `admin.js:884` | 源码公开即可伪造任意 token，生产应直接 500 |
| 3 | `/d1-batch` 接受任意 SQL，无白名单 | `routes.js:355-386` | 单密钥可 `DROP TABLE` / 提权 / 读密码哈希 |

附带的第 4 项（隐蔽但同等严重）：**md 正文零消毒**。HTML 走 `scrubHtml()`，md 走 `marked.parse()` 无 sanitize，出口有 4 处（`admin.js:639`/`3018`、`documents.js:389`、`routes.js:930`）⇒ 存储型 XSS。

另：`/d1-batch` 批次上限 200 > 免费档 50 子请求 ⇒ 超 50 条中途失败、**部分成功导致数据不一致**。

## 四、建议的产品线切法（本次结论）

### 4.1 定一条主线，其余降级为配套

**主线：Worker CMS 独立成唯一真源**，独立仓库（建议 `cf-cms`），拥有 `src/` + `wrangler.toml` + `schema.sql` + 部署脚本 + 对外文档。

**边界只有一条：API 契约**（WPv2 兼容层 + 应用密码 + 应用密钥分离）。所有配套件只依赖契约，不依赖彼此。

### 4.2 同步插件的分层（按用户思路落地）

| 层 | 内容 | 默认 |
|---|---|---|
| 基础层 | 只写 D1 数据：文章 / 分类 / 标签 / 媒体；删旧 R2 单页 | 始终启用 |
| 高级层 | 一键部署 Worker、模板/风格资源上传 | **默认关闭**，需显式开启 |

同插件内不拆 ✅ 符合用户设想。
但要加一条硬约束：**插件内不再保留 `worker/` 源码副本**。高级层需要部署能力时，走「下载 CMS 发行包」而不是「读本地副本」。

### 4.3 配套件独立存活

- **CFSE Style**：只依赖「风格包格式」，不依赖 CMS 也能用（可导入任意静态站）。
- **静态托管插件**：本来就独立，跟 CMS 保持弱关联。
- **MD 编辑器 / Obsidian**：只依赖 WPv2 契约。

## 五、待用户拍板的开放问题

1. **多租户？** —— `docs/hosting-config-context.md:33,43` 明确推迟：若做 SaaS 多租户须单独立项（要改 schema + 所有查询 + 防跨租户泄漏）。**独立产品是「自托管单站」还是「多租户 SaaS」，决定整个 schema 走向，必须先定。**
2. **公开还是私有？** —— `cf-static-hosting` 已转 private；CMS 若要对外发布需过一遍开源合规（密钥历史、`.gitignore` 已排除 `worker/wrangler.toml` ✅）。
3. **文档库是「剥离」还是「砍掉」？** —— `cf-docs` 已独立上线可用，剥离意味着主仓删除 + 清 R2 成品 + DROP 表（设计稿 S12 决定不迁移数据）。
